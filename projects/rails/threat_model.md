# Ruby on Rails threat model

## What Rails is

A full-stack web framework. A Rails application is the application developer's Ruby code running on top of the
frameworks in this repository. Each framework lives in its own top-level directory with its own `lib/`, `test/` and
`bin/test`:

- `actionpack/` (Action Dispatch, Action Controller): request parsing, routing, middleware, sessions, cookies, CSRF
  protection, strong parameters, redirects, `send_file`/`send_data`, Content-Security-Policy.
- `actionview/`: templates, HTML escaping and the tag, form, URL, text, asset and sanitize helpers.
- `activerecord/`: the ORM, SQL generation and quoting for SQLite, PostgreSQL, MySQL/MariaDB (mysql2, trilogy), Active
  Record Encryption, signed ids, `has_secure_token`.
- `activemodel/`: validations, attribute type casting, `has_secure_password`.
- `activesupport/`: `MessageVerifier`, `MessageEncryptor`, `KeyGenerator`, `EncryptedFile`/credentials, JSON
  encoding/decoding, `ERB::Util` escaping, `SafeBuffer`, inflector, number/time parsing, caching stores.
- `activestorage/`: uploads, blobs and variants, the blob/representation/disk/direct-upload controllers, image and
  video analyzers and previewers (shells out to libvips, ImageMagick, ffmpeg, mupdf, poppler).
- `actionmailbox/`: inbound email ingress controllers (Mailgun, Mandrill, Postmark, SendGrid, relay) and routing.
- `actiontext/`: rich text storage, sanitization and rendering, attachments addressed by signed global ids.
- `actioncable/`: WebSocket server, connection identification, channel subscription, broadcasting.
- `activejob/`, `actionmailer/`: argument serialization (Global ID), mail rendering and delivery.
- `railties/`: application boot, configuration defaults, the `rails` CLI, generators, built-in controllers
  (`/up` health check, info/mailer previews in development).

## Who the attacker is

A remote, unauthenticated or low-privilege user of a Rails application, sending HTTP requests, WebSocket frames,
uploaded files, or inbound email to an application that uses Rails as documented. Findings should name the public API
or default behavior the attacker reaches, not a contrived application that misuses an API whose documentation warns
against exactly that use.

Assess against an application generated by `rails new` on `main` with the defaults from
`config.load_defaults` for the current version, and say if a finding depends on an older default or a non-default
setting.

## Where untrusted input enters

- Everything in the HTTP request: path, query string, form and multipart bodies, JSON bodies, headers (Host,
  X-Forwarded-*, Accept, Content-Type, Range, If-None-Match, Origin, Referer), cookies. Parsing in
  `actionpack/lib/action_dispatch/http/` (`param_builder.rb`, `query_parser.rb`, `mime_negotiation.rb`,
  `request.rb`, `upload.rb`) and the routing journey in `actionpack/lib/action_dispatch/journey/`.
- Signed, encrypted and session cookies and every other signed or encrypted token a client can hold: message
  verifiers, signed blob ids, signed global ids, signed record ids, `generates_token_for` tokens, CSRF tokens.
- Values the application passes straight from params into documented-safe framework APIs: hash conditions and
  bind parameters in `where`/`find_by`/`order` with a hash/symbol, `sanitize_sql_*`, attribute assignment through
  strong parameters, `url_for`/`redirect_to` with a hash, tag/content helpers, `sanitize`, `link_to`, `number_to_*`,
  `time_ago_in_words`, `ActiveSupport::Inflector`, `Time.zone.parse`, `Date.parse`-backed type casting.
- Uploaded files and their declared filename/content type, processed by Active Storage analyzers, variants and
  previewers.
- Inbound email: raw MIME posted to ingress controllers, and the ingress authentication itself.
- Rich text HTML submitted to Action Text.
- WebSocket frames and channel identifiers sent to Action Cable.
- Database contents written earlier by a remote user, when Rails later renders, deserializes or interprets them.

## Trusted (out of scope)

- The application's own code, templates, routes, configuration, credentials and `secret_key_base`.
- The database server, cache store, job queue backend and storage service, and anything read back from them that a
  remote user could not have written. `Marshal` in cache and job payloads is a documented trust boundary.
- Developer-only surfaces: the console, generators and their arguments, rake/`bin/rails` tasks, migrations,
  fixtures, development-only routes (`/rails/info`, mailer previews, Action Mailbox conductor) and error pages shown
  with `consider_all_requests_local`. Do report if one of these is reachable in the production environment by
  default.
- Explicit opt-outs documented as unsafe with untrusted input: `html_safe`, `raw`, `<%==`, `render inline:`,
  `render file:` / `send_file` with user-chosen paths, raw SQL string fragments and `Arel.sql`, `permit!`,
  `redirect_to` with `allow_other_host: true`, `constantize`/`safe_constantize` on user input, `YAML.unsafe_load`.
- Third-party gems Rails depends on but does not maintain here (rack, rails-html-sanitizer, loofah, nokogiri,
  globalid, mail, bcrypt, image_processing, ruby-vips, mini_magick, the database drivers). Report a bug in how Rails
  calls them; report a bug in the gem itself to that project.
- Test helpers, `tools/`, `guides/`, and JavaScript packages' development tooling.

## Components that matter most

1. Request parsing, routing, cookies/sessions, CSRF, host authorization, `remote_ip`, redirects and `send_file`
   (Action Pack).
2. HTML escaping and helpers (Action View, `ActiveSupport::SafeBuffer`, `ERB::Util`).
3. SQL generation and quoting reached through documented-safe Active Record APIs, per adapter.
4. Message signing/encryption and every token built on it (Active Support, Active Record signed ids and
   encryption, Active Storage blob URLs, Action Text attachments).
5. Active Storage controllers and file processing; Action Mailbox ingress authentication; Action Cable connection
   and channel authorization.
6. Secure defaults written by the app generator and `load_defaults` (CSP, `force_ssl`, filter parameters,
   generated Dockerfile).

## How to exercise it

Run `rails-services-start` first. Every framework has its own suite, run from its directory:
`cd actionpack && bin/test test/dispatch/request/json_params_parsing_test.rb`,
`cd activerecord && bundle exec rake test:postgresql TEST=test/cases/sanitize_test.rb`.
Integration-style request tests live under `actionpack/test/dispatch/` and `actionpack/test/controller/`;
`ActionDispatch::IntegrationTest` drives a full middleware stack. Active Storage and Action Mailbox tests boot a
dummy application under `test/dummy`. Railties' generator and application tests generate and bundle real apps; run a
single file with `bin/test`, or the whole suite with `bundle exec rake test`, which runs each file in its own process.

## How we rate severity

- Critical: remote code execution; authentication bypass or session/cookie forgery without the secret; SQL
  injection through a documented-safe API; arbitrary file read or write from a request; decrypting or forging a
  signed/encrypted message without the key.
- High: XSS through a helper or escaping path that claims to escape; CSRF protection bypass; open redirect through
  `redirect_to` under default settings; access to another user's Active Storage blob or Action Text attachment;
  Action Mailbox ingress authentication bypass; Action Cable channel authorization bypass; leaking secrets or
  credentials in production responses or logs (filter parameters).
- Medium: denial of service from a single small request (ReDoS, quadratic parsing, memory amplification),
  cache poisoning through header handling, header injection, information disclosure that does not expose secrets.
- Low: issues that need an unusual non-default configuration, or that only weaken defense in depth.

Ruby's regexp timeout and memoization reduce ReDoS impact; rate a ReDoS by its time under current Ruby with input
that fits within default request size limits.

## Reports and patches

- Name the framework, file and public API, and the oldest supported release series affected if you can tell
  (see `guides/source/maintenance_policy.md`).
- Reproduce with a failing test in that framework's suite, or a single-file script in the style of
  `guides/bug_report_templates/`, rather than a full application.
- Patch against `main`, with the test, following the surrounding code's style. Keep the fix minimal; we backport it
  to stable branches ourselves.

## Already known; don't report

- That raw SQL fragments, `html_safe`, `render inline:`, `permit!`, `Marshal` in caches, or the other opt-outs
  above are unsafe with untrusted input.
- Missing security headers or rate limits that the application is expected to configure.
- Timing differences in non-secret comparisons; denial of service that needs gigabyte-sized requests or sustained
  floods.
