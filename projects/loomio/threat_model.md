# Loomio security guidance

Loomio is an open-source collaborative decision-making web application used by groups to discuss proposals and vote. It runs as a hosted service and on self-hosted installations. Private discussions, membership records, account access, and the integrity and privacy of ballots are security-sensitive. Scan the current `master` branch, including the Rails application, Vue client, collaborative editing server in `hocuspocus/`, incoming mail code in `haraka/`, and mobile push relay in `push-relay/`.

## Trust boundaries and intended guarantees

- Check signed-out/public users, ordinary members, poll participants, topic guests, coordinators/group administrators, instance administrators, and operators with database or backup access separately. Access to one group or topic must not grant access to another. Revoked or inactive memberships and invitations must not preserve unintended access.
- Review public and private groups, direct and group topics, active and closed polls, every `hide_results` mode, anonymous and identified polls, quorum behavior, and administrator-only feature flags. Use the reusable fixture matrix rooted at `topics(:discussion_topic)` and `topics(:direct_topic)`; its roles include conflicting account, membership, and topic preferences.
- Enforce authorization on server reads and writes, including related records, nested serializers, search, timeline events, realtime subscriptions, background jobs, notifications, mail, and CSV/JSON exports. UI hiding is not an access control. Check composition attacks that join otherwise innocuous records by IDs, timestamps, ordering, or shared events.
- For anonymous polls, trace identity and ballot information through storage, shared serializers, APIs, live updates, notifications, mail, exports, backups, and jobs. Distinguish application-level disclosure to participants or administrators from what an operator can infer from database or backup access. Inspect the actual storage design and anonymity invariants before asserting a breach; do not assume closing a poll is sufficient protection.
- Voting operations must preserve voter eligibility, vote limits, ballot integrity, visibility settings, and atomic changes to domain records and events. Failed operations must not leave partial state or broadcast rolled-back records.
- Review session creation, rotation, expiry, revocation, logout, impersonation, CSRF protection, token scope, cookie flags, passkeys, SAML integration, and cleanup of dependent session records. Test both successful and rejected requests; test mode disables CSRF, so assess production configuration separately.
- Treat rich text, uploaded attachments, URLs and link previews, inbound email, webhook payloads, collaborative editing messages, invitation and authentication tokens, and all API parameters as untrusted input. Check stored/reflected XSS, injection, SSRF, path traversal, unsafe file handling, and unintended outbound requests. Inspect production settings before reporting test-only configuration as a vulnerability.

## Scope and severity

Prioritize reproducible application vulnerabilities over dependency version warnings without a reachable Loomio exploit. Production and deployment code are in scope. Development scenario endpoints and test fixtures are not production attack surfaces unless they can be enabled or reached in production. The private subscription engine sometimes mounted under `engines/loomio_subs` is not present in this public checkout and cannot be assessed here.

Rate severity by demonstrated impact, required privileges, affected users/groups, and exploit prerequisites. Unauthenticated remote code execution or broad account compromise can be critical; cross-group access to private content, unauthorized voting, or recovery of protected anonymous ballot identities can be high depending on reach and prerequisites. Administrator-only configuration changes and possession of a server's secrets do not by themselves demonstrate a lower-privilege exploit. Describe any limitations rather than assuming missing exploit steps.

## Build and reproduction

The Dockerfile installs Ruby, Node, locked Ruby and JavaScript dependencies, image-processing utilities, and PostgreSQL, builds Vue assets, and prepares a local test database. The checkout is `/src`. No production credentials or external services are needed. In the scanner shell, run `loomio-test` for the Rails suite or `loomio-test bin/rails test test/services/anonymous_ballot_service_test.rb` for a focused test. `loomio-test bin/rails server -b 127.0.0.1` starts the application in test mode after starting PostgreSQL.

JavaScript checks run with `(cd /src/vue && npm run test:unit && npm run test:component)`, `(cd /src/hocuspocus && npm test)`, `(cd /src/haraka && npm test)`, and `(cd /src/push-relay && npm test)`. Browser E2E tests require additional Chrome/ChromeDriver setup and are not supplied by this image. Never run Rails and E2E tests concurrently because they share the test database. Rails tests use WebMock to disable non-local network requests. Production-only security behavior needs focused tests or inspection beyond this test-mode server.

Provide a minimal local reproduction or focused regression test, the affected entry point and authorization boundary, prerequisites, impact, and a proposed patch when feasible. Preserve confidential reports and send them to the configured primary contact. Follow the repository's `SECURITY.md` for private advisory handling; do not open public vulnerability issues.
