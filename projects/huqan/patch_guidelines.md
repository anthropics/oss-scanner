# How we would like patches made

## Size and scope of a fix

- As narrow as possible. Change the faulty function, not its callers' style.
- When the same mistake is repeated, fix the shared helper once rather than each
  call site — but only when the call sites genuinely share a root cause. Say which
  case it is in the patch description.
- Do not refactor, rename or reformat around the fix. A review diff that mixes a
  one-line fix with a tidy-up takes longer to review than the fix is worth.
- Do not add an abstraction, a config flag or a feature toggle for the fix. If a
  behaviour needs to be optional, that is a separate discussion, not part of a
  security patch.

## Code style

- Match the surrounding file. The repository is CommonJS (`'use strict';` at the
  top, `require`, `module.exports`), two-space indent, single quotes.
- Comments: only where the code is not obvious. Do not narrate the change or cite
  this patch in a comment. The reasoning belongs in the patch description and the
  commit message.
- Fail closed. A guard that returns "allow" when it cannot decide is not a fix; a
  guard that throws or refuses is. This is the same rule the runtime follows.

## Tests

- Add a regression test to the nearest existing file under `test/`. Do not create a
  new test file when one already covers the area.
- The test must fail on the unfixed code and pass on the fixed code. Say in the
  patch description which command you ran.
- Tests run through `node scripts/run-tests.js <file>` (or `npm test` for the whole
  suite). They must pass with no network access, because the suite is run offline
  and the scanner's analysis phase has no Internet.
- Do not weaken, skip or delete an existing test to make a patch pass. If an
  existing test now fails, the fix is wrong or the test encodes the old contract;
  say which and why.

## Branch and commit message

- Against `main`.
- Subject line in the form `component: what changed`, imperative, lower case after
  the colon — e.g. `tool-call-gate: refuse an allow decision with no approval`.
- One commit per fix unless the repository requires a signature flow that forces a
  separate commit.
- Do not include an AI or agent signature, co-author trailer, or "generated by"
  line in the commit message or the patch description.
