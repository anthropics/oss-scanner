# How we would like reports written

## Layout and length
Use a concise report with these sections: Summary, Affected code and versions,
Prerequisites, Impact, Reproduction, and Suggested fix. Keep one root cause per
report.

## What every report should state
Identify the affected component and code path, attacker starting position,
required roles or configuration, and the security boundary or data at risk.
Include reproducible steps and distinguish confirmed behavior from assumptions.

## Style
Use plain, precise language. Avoid overstating impact. Include enough detail
for a maintainer to reproduce the issue without relying on unstated environment
assumptions.
