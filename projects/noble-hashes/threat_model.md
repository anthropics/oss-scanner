# Threat model: noble-hashes

## What this project does and where untrusted input enters
Audited and minimal JS implementation of hash functions, MACs and KDFs: SHA-1/2/3, SHAKE, cSHAKE/KMAC/TupleHash/ParallelHash/TurboSHAKE/KangarooTwelve, RIPEMD-160, BLAKE1/2/3, HMAC, HKDF, PBKDF2, scrypt, Argon2 and ESKDF.

It is a library: it has no network listener, no CLI and no file I/O. Untrusted input arrives through its public
API, called by applications in Node.js, Deno, Bun and browsers. Assume every byte array, hex string, bigint,
number and options object passed to an exported function may be attacker-controlled, unless the README documents
that argument as trusted (for example a secret key generated by the caller).

## Components that matter most / least
- Every hash, XOF, MAC and KDF in `src/`. Highest priority: `sha2.ts`, `sha3.ts`, `hmac.ts`, `hkdf.ts`,
  `pbkdf2.ts`, `scrypt.ts`, `argon2.ts`, `blake2.ts`, `blake3.ts`, and the shared helpers `_md.ts`, `_u64.ts`,
  `utils.ts`.
- Incremental hashing (`create().update().digest()`), `clone()`, `destroy()`, and state reuse between calls:
  wrong output when messages are split at block boundaries, or state leaking between instances, is in scope.
- Parameter validation on KDFs (scrypt N/r/p, argon2 t/m/p, dkLen, output lengths), integer overflows in length
  arithmetic, and XOF output lengths.
- `webcrypto.ts` is a thin wrapper; bugs in how it forwards arguments are in scope.
- `legacy.ts` (SHA-1, MD5, RIPEMD-160) is in scope for correctness; their known cryptographic weaknesses
  are not.

## How to exercise it
- Source is TypeScript under `src/`; `npm run build` (tsc) emits the shipped .js next to it. Tests import the
  built output via package exports, so rebuild after editing source.
- `npm test` runs the fast suite (`node test/index.ts`); individual files run with `node test/<name>.test.ts`.
- Test vectors (Wycheproof, ACVP, RFC/KAT) are under `test/vectors/` (ACVP vectors come from the `test/vectors/acvp-vectors` submodule). Reproducers are best written
  as a small `node repro.ts` script that imports the package by path and compares against a vector or a
  reference implementation.
- Slow suites: `npm run test:slow`, `test:dos`, `test:kdf`, `test:acvp`.

## How you rate severity
- **Critical**: an attacker who controls only public inputs (signatures, public keys, ciphertexts, messages,
  encoded points) can recover a secret key, forge a signature/MAC/tag, or decrypt; or a valid output is
  produced for the wrong input in a way an application relies on (e.g. `verify` returns true for an invalid
  signature).
- **High**: incorrect output for valid inputs (wrong hash/ciphertext/shared secret, non-interoperable
  results), accepting malformed or non-canonical encodings where the spec requires rejection (malleability),
  missing input validation that lets a caller silently get insecure results, or nonce/randomness misuse
  inside the library.
- **Medium**: timing differences on secret data that are measurable in a realistic harness and are not one of
  the documented limitations below; prototype pollution or option-object confusion reachable through the API.
- **Low**: denial of service through unbounded CPU or memory on attacker-controlled sizes, when the
  parameter is something an application would plausibly pass through from an attacker; exceptions of the
  wrong type or with confusing messages.
- A finding needs a reproducer that runs against the built package. Report the spec, RFC or test vector the
  behaviour violates.

## Anything to leave alone
- Constant-time execution is a goal at the algorithm level only. JIT, garbage collection and bigint
  arithmetic make strict constant-time impossible in JavaScript; do not report generic "JS is not
  constant-time" or "bigints are not zeroized" issues.
- Secrets staying in memory (immutable strings and bigints, buffers not zeroized, values held across `await`)
  are documented and out of scope.
- The quality of `crypto.getRandomValues` is out of scope.
- `benchmark/`, `test/`, `audit/` and dev dependencies (jsbt, prettier, typescript, bismar, fast-check) do not
  ship to users and are out of scope, except where a test itself is wrong and hides a real bug.
- Please keep patches minimal, in the existing code style, and add a regression test next to the related
  tests.
- Very large but valid KDF parameters taking a long time is expected behaviour; the async variants exist for that.
