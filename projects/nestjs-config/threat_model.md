# Threat model

## What this project does and where untrusted input enters
`@nestjs/config` loads configuration for NestJS applications. It reads `.env` files (dotenv, with
optional dotenv-expand variable expansion), merges them with `process.env` and with custom
configuration factories (`load`, `registerAs`, `forFeature`), validates the result (a `validate`
function, or a Standard Schema `validationSchema` such as Zod), and exposes it through
`ConfigService.get()` / `getOrThrow()` / `set()` with dot-path access.

Configuration sources are normally controlled by whoever deploys the application, not by remote
clients, so the attack surface is small. The places where less trusted data can still reach this
package's code:

- **`.env` parsing and expansion**: `lib/config.module.ts` (`loadEnvFile`, `assignVariablesToProcess`)
  and the default parser in `lib/utils/get-default-parser.util.ts`. Env files are sometimes shared
  across teams, generated by CI, or mounted from secret stores, and their keys are copied onto
  `process.env`.
- **Validation**: `lib/utils/validate-with-schema.util.ts` and the validation branches in
  `lib/config.module.ts`. Values that skip a validator the application configured, or are replaced
  after validation, are in scope.
- **Path-based access**: `lib/config.service.ts` (`get`, `getOrThrow`, `set`, the internal cache) and
  `lib/utils/merge-configs.util.ts` resolve dot paths with `es-toolkit` `get` / `set`. Applications
  occasionally pass dynamic keys (for example a tenant or feature name) to `get()`; prototype
  pollution or reads outside the configuration object through such a path are in scope.
- **Precedence and override rules**: `ignoreEnvFile`, `ignoreEnvVars`, `skipProcessEnv`,
  `expandVariables`, `override`, `envFilePath` ordering, `validatePredefined`. A documented
  precedence that is not honoured, so that a lower-priority source silently wins, is in scope.

## Components that matter most / least
- Most: `lib/config.module.ts` (loading, expansion, validation, writing to `process.env`),
  `lib/config.service.ts` (path access, cache, `set`, change events),
  `lib/utils/merge-configs.util.ts`, `lib/utils/validate-with-schema.util.ts`.
- Less: `lib/conditional.module.ts` (`ConditionalModule`, reads a single env variable), typings
  under `lib/types` and `lib/interfaces`.
- Out of scope: `tests/` (test suites and fixtures), and vulnerabilities that live entirely in
  `dotenv`, `dotenv-expand` or `es-toolkit` unless this package's own use of them makes the issue
  reachable.

## How to exercise it
- After the Docker build, the library is compiled into `dist/`. Tests: `npm run test:integration`
  (vitest). The specs in `tests/e2e` boot `tests/src/app.module.ts` with different module options
  and `.env` fixtures; adding a spec there is the easiest way to reproduce an issue.

## How you rate severity
- Critical: code execution caused by the contents of a `.env` file or of an environment variable,
  under default options.
- High: prototype pollution through `.env` keys, environment variable names, or a path passed to
  `ConfigService.get()` / `set()`; a configured validator that is skipped or whose result is
  discarded, so unvalidated values reach the application.
- Medium: a documented precedence or override rule that is not honoured (e.g. `.env` overriding an
  already-set `process.env` value without `override`); secrets from configuration exposed in
  thrown error messages; issues that need an uncommon but supported option combination.
- Low: issues that need write access to the deployment's environment or env files, or the
  application developer opting in to clearly unsafe behaviour.

## Anything to leave alone
- Do not report that an attacker who can already write the application's `.env` file or its
  environment can change its configuration. That is the purpose of the package.
- Do not report that `expandVariables` expands references to other variables. That is documented
  behaviour; report only expansion that reaches something it should not (e.g. code execution,
  unbounded recursion or memory growth from a short file).
- Reports should include a minimal reproducer (a spec in the style of `tests/e2e`, plus any `.env`
  fixture it needs) and a patch against `lib/` where possible.
