# Threat model

SGLang-Omni serves audio models (TTS, ASR, diarization, voice chat) and unified multimodal models (UMMs) behind an OpenAI-compatible HTTP and WebSocket API, with Python and Rust request routers, native C++ MLX servers for Apple Silicon, web playgrounds, and the Voxt macOS app. Please audit the whole repository. Every component below is in scope unless the last sections say otherwise, and the tiers only set the order of attention. When a document under `docs/` disagrees with the code, trust the code (see "Documentation that may not match the code").

## What this project does and where untrusted input enters

### Deployment shapes

1. **Server.** `sgl-omni serve` (`sglang_omni/cli`, `sglang_omni/serve`) runs one FastAPI process that hands each request to a multi-stage pipeline. It binds `0.0.0.0:8000` unless `--host` and `--port` are given, and falls back to a random free port when the port is busy unless `SGLANG_OMNI_STRICT_PORT=1`.
2. **Stage processes on one host.** Stages run in separate processes and GPUs. Control and data travel over Unix sockets in a per-run directory under `endpoints.base_path` (default `/tmp/sglang_omni`) and through shared memory or CUDA IPC relays. Tensor-parallel groups and weight update groups use torch.distributed rendezvous ports, and native SGLang engines inside stage processes open their own scheduler, master, and HTTP ports. Mooncake, NIXL, and NCCL relays exist in `sglang_omni/relay` and matter when a deployment wires remote edges.
3. **Routers.** A Python router (`sglang_omni_router/python`: single-process app, or a supervisor with a control plane and data planes, plus a launcher for managed workers) and a standalone Rust router (`sglang_omni_router/rust`) spread requests over many servers. The Python router binds `0.0.0.0` by default, and the Rust router listens where its TOML says (the shipped examples use `0.0.0.0:30000`).
4. **Local desktop.** Voxt (`Voxt/`, Swift) runs speech features on a Mac and can call remote ASR and LLM services. The shipped app runs ASR in process, and the Omni Dev build supervises the native C++ servers in `sglang_omni_mlx/native` on loopback.
5. **Demos and tooling.** Playgrounds (`playground/gradio`, `higgs`, `qwen-omni`, `realtime`, `s2pro`), example launchers (`examples/`), benchmarks (`benchmarks/`), and CI harnesses. Users run them as shipped, often on shared machines, and several bind all interfaces.

### Attackers to consider

- **A1. Unauthenticated network client** of the server, either router, a playground, an example server, a native server, or a stage that exposes HTTP routes.
- **A2. Co-tenant client** of a shared deployment who targets other clients' requests, outputs, sessions, streams, cached state, uploaded voices, stored media or video jobs, request IDs, or the admin functions.
- **A3. Hostile remote host** that SGLang-Omni contacts because of a request, config, or registration: media URLs and their redirects, router worker URLs and their health replies, a weight update `master_address`, Hugging Face Hub or `HF_ENDPOINT`.
- **A4. Hostile bytes** in requests: audio, image, video, containers, encoded codec tokens, token IDs, tensors, JSON, and multipart bodies.
- **A5. Cluster neighbor** that can reach torch.distributed rendezvous ports, native engine ports, router control ports, metrics, or remote relay endpoints when a deployment wires them.
- **A6. Browser-driven attacker.** A web page in a user's browser that sends cross-site HTTP or WebSocket requests, or uses DNS rebinding, against any SGLang-Omni listener the browser can reach, including loopback.
- **A7. Another local user or process** on the same host, through shared `/tmp` paths, Unix sockets, shared memory, port claim files, caches, and state directories.
- **A8. Network attacker or hostile endpoint around Voxt**: remote ASR and LLM endpoints, redirects, downloads, and the update and release-notes channel.
- **A9. Outside contributor** acting through pull requests, comments, or labels on the GitHub Actions workflows and the self-hosted runners.
- **A10. Supply chain**: installers, Dockerfiles and image entrypoints, dependency indexes and pins, GitHub Actions pins, and everything fetched during install, CI, model provisioning, and benchmarks.

Trusted: the operator's command line, config files, and environment, and the model repository or directory the operator chose. Config values are powerful on purpose (see "Config, loading, and platform"), so any path by which request data reaches them is in scope.

## Components and entry points

### 1. HTTP API server

Code: `sglang_omni/serve` (`openai_api.py`, `protocol.py`, `openai_errors.py`, `streaming.py`, `launcher.py`, `server_warmup.py`, `stage_routes.py`, `speech_*.py`, `transcriptions.py`, `translations.py`, `speech_to_text.py`, `transcription_chunking.py`, `subtitles.py`, `transcription_adapters/`, `diarizations.py`), `sglang_omni/http`, `sglang_omni/admission.py`, and `sglang_omni/client`, which is the in-process bridge from every route into the pipeline.

- Routes: `GET /health`, `GET /v1/models`, `GET /favicon.ico`, `POST /v1/chat/completions`, `POST /generate`, `POST /v1/images/generations`, `POST /v1/images/edits` (multipart file or URL), `GET|POST /v1/audio/voices`, `DELETE /v1/audio/voices/{name}`, `POST /v1/audio/speech`, `GET /v1/audio/speech/{request_id}`, `POST /v1/audio/speech/batch`, `POST /v1/audio/transcriptions`, `POST /v1/audio/translations`, `POST /v1/audio/diarizations`, `GET /v1/realtime/capabilities`, and every route a stage mounts through `http_routes` (`stage_routes.py`, which relays frames to a stage process).
- Parameter channels that reach model code: `/generate` copies client `metadata` and `stage_params` into the pipeline request and accepts `input_ids`, `prompt`, `messages`, `sampling_params`, `stage_sampling`, `output_modalities`, and `multimodal_train_inputs`. `/v1/chat/completions` carries `stage_params`, `stage_sampling`, `audio` (copied into `metadata["audio_config"]`), `audios`, `images`, `videos`, `video_fps`, `video_max_frames`, `video_min_pixels`, `video_max_pixels`, `video_total_pixels`, `use_audio_in_video`, talker sampling fields, and a client-chosen `request_id`. Check that these channels cannot set internal metadata keys (`omni_session`, `omni_continuation`, `umm_context`, `generation_deadline`, `task`, `tts_params`, `image_generation`, `uploaded_voice_name`, `uploaded_voice_created_at`) or skip the validation that the dedicated routes apply.
- Uploaded voices: created, listed, overwritten, and deleted through `/v1/audio/voices`, stored on disk (`SPEAKER_SAMPLES_DIR`, `SPEAKER_MAX_UPLOADED`), and used by name in speech requests. Check ownership, exposure of consent text and transcripts, size and count bounds, name handling on disk, and persistence.
- Request IDs: chosen by clients on several routes and used for result lookup (`/v1/audio/speech/{request_id}`), aborts, tombstones, relay object IDs, and seed derivation. Check collisions between clients.
- Bodies and uploads: check the size, duration, and count bounds of every JSON body, multipart upload (transcription, translation, diarization, image edit, voices), batch, and streamed response, and the bounds of `transcription_chunking`.
- Errors: check what exception text, paths, URLs, and internal hosts reach clients through `openai_errors.py`, speech error mapping, and `/generate` details.
- CORS and Origin: check the CORS policy of every app and the Origin handling of every WebSocket (A6).

### 4. Media, files, and decoders

- Policy: `sglang_omni/preprocessing/resource_connector.py` and `base.py`, set by `--allowed-local-media-path` and `--allowed-media-domain` or `SGLANG_OMNI_ALLOWED_LOCAL_MEDIA_PATH` and `SGLANG_OMNI_ALLOWED_MEDIA_DOMAINS`. The CLI help documents that `file://` is off without an allowed directory, that bare local paths stay allowed by default, and that remote media from public hosts is allowed when no domain is set. Check every connector instance (the global one used by chat, vision, video, and ASR, the TTS reference connector, and per-request connectors in model code) for loopback, private, link-local, and metadata addresses, redirects, DNS changes between check and use, size caps, timeouts (`REQUEST_TIMEOUT`), and symlinks.
- Fetch and open points outside the connector: `sglang_omni/utils/audio.py` `load_audio` (http and https with redirects, data URIs, `file://`, bare paths), `sglang_omni/preprocessing/transcription.py` `police_request_audio` and `prepare_audio`, `sglang_omni/modules/ming_audio/audio_media.py`, and model code such as `auk/request_builders.py`, `moss_tts/reference_encoder.py`, `higgs_tts/utils.py`, `zonos2/components/speaker_encoder.py`, `ming3_audio/stages.py` and `talker.py`, `ming_omni` audio loading, `ming_tts` `torchaudio.load`, and the external `qwen_tts` package. Each one is a policy enforcement point.
- Documented features that name server files: PersonaPlex `stage_params.preprocessing.voice` (paths and `.pt` files read with `torch.load`), Cosmos 3 generation `image_path`, `video_path`, and `control_path`, reference `audio_path` fields in TTS requests, and the native MLX `vad_model_directory`. Check each against the configured media policy.
- Decoders reached by request bytes: FFmpeg through torchcodec, PyAV, librosa and audioread, soundfile, Python `wave`, decord, Pillow, openai-whisper log-mel, and the `ffmpeg` CLI subprocess in `zonos2`. Also request-supplied codec codes and IDs that index GPU tables (Higgs `reference_codes`, S2-Pro and Drama 3 `references[].vq_codes`, Qwen3-Omni `input_ids`, `multimodal_train_inputs`, and the raw `speaker_id` fallback).
- Size knobs: video frame and pixel budgets, image `num_inference_steps` and `decoder_steps`, `max_new_tokens` per model, `hotwords`, reference audio durations, and LLaDA2-Uni `decode_mode` switches that reload weights.

### 5. Shared UMM serving runtime

`sglang_omni/pipeline/umm.py` runs interleaved requests on the multi-stage pipeline: `UMMController` (the entry stage scheduler), the `UMMAdapter` contract (`start`, `advance`, `usage`, `close`), `UMMStep` with parallel `dispatches`, `UMMOutputRelay` (the in-process output stage), `route_umm`, `umm_stream_done_targets`, and `UMMPipelineConfig`. The first consumer is Cosmos 3 (`sglang_omni/models/cosmos3/umm.py`, `umm_config.py`), served by the native chat stage (`sglang_omni/scheduling/native_chat_scheduler.py`) and the native generation stage (`sglang_omni/native_generation`: `stage.py`, `media.py`, `cancellation.py`). Check:

- Continuation identity: every dispatch carries `execution_id`, `index`, `phase`, `stage`, and a `nonce` in request metadata, and only the expected continuation may advance a request. Late, duplicate, forged, or cross-request results must never create turns, segments, or context.
- Bounds: `max_dispatches`, `max_outputs`, `max_active`, `max_retained_bytes`, and `timeout_s`, their error classes (client error before the first dispatch, server error after, 503 for admission and shedding), retained bytes reported by `usage`, one phase per stage per step, and `close` exactly once per request for every reason (`completed`, `failed`, `aborted`, `expired`, `shed`, `shutdown`).
- `ContextRef` handoff of engine-owned context such as KV pages: ownership, release on every close path, and whether one request can name another request's context.
- Output: segment order and contiguity (`execution_id`, `segment_index`, `kind`, `data`), inline media limits (size cap, MIME allowlist, SHA-256, data URL encoding), and delivery through the SDK, `/generate`, and `/v1/chat/completions`.
- Cancellation: client disconnect, deadline, shedding, and failure must stop further dispatches and abort queued and running phase work at every stage, including native engines.
- Native chat stage: which native `ChatCompletionRequest` fields clients can set through `stage_params` and `stage_sampling`, and media policing of `image_url`, `video_url`, and `audio_url` parts.
- Native generation stage: its client field allowlist, `*_path` media handling against the server media policy, remote fetch size, ownership and deletion of saved media, video jobs and their retrieval, content, and deletion by ID (`/v1/images`, `/v1/videos`, `/v1/actions` mounted from the stage), per-request deadlines, and cancellation outside single-GPU mode.

### 6. Pipeline runtime and stage IPC

`sglang_omni/pipeline` (`coordinator.py`, `control_plane.py`, `stage/`, `local_dispatch.py`, `mp_runner.py`, `runtime_config.py`, `stage_workers.py`, `replicas.py`, `weight_share.py`, `tp_control.py`, `sessions.py`), `sglang_omni/comm` (`stage_io.py`, `data_ref.py`, `engine.py`, `kv_transfer.py`, `router.py`), `sglang_omni/relay` (`shm.py`, `cuda_ipc.py`, `mooncake.py`, `nccl.py`, `nixl.py`), `sglang_omni/proto` (all wire schemas, including `session.py`), `sglang_omni/scheduling` (`omni_scheduler.py`, `simple_scheduler.py`, `threaded_simple_scheduler.py`, session schedulers, `pd_scheduler.py`, `dllm_scheduler.py`, Code2Wav and streaming vocoder schedulers, `pipeline_state.py`, `typed_tensor.py`), `sglang_omni/model_runner`, and `sglang_omni/mps`. Check:

- Who can reach the per-run IPC directory and its sockets, how the directory and its parent are created and owned, and what a local user (A7) can do by connecting or pre-creating paths, given that stage traffic is deserialized with pickle in several places (`DataRef` headers, CUDA IPC headers and tensor bytes, inline stream chunks, TP queues, stage route frames, `broadcast_pyobj`).
- Torch.distributed rendezvous for TP groups (ports claimed from 29500), weight update groups, native engine ports, and the loopback rendezvous in model code (`llada2_uni` decoder runtime, MiniCPM-o and Ming-Omni encoders with `MASTER_ADDR`), against A5 and A7.
- Remote relays when wired: authentication and integrity of Mooncake, NIXL, and NCCL transfers.
- Cancellation: aborts over ZMQ PUB and SUB without acknowledgement, TP follower aborts, native engine aborts, and what happens when a subscriber is full or the abort listener fails.
- Bounds: coordinator in-flight and session caps, stream backlog accounting, per-request stream queues and fan-in buffers, the CUDA IPC pool, and shared memory slot sizing.
- Admission (`sglang_omni/admission.py`, `OmniScheduler` admission) and shedding under load.
- CUDA MPS lifecycle (`/tmp/sglang-omni-mps-<user>`, `nvidia-cuda-mps-control` resolved through `PATH`).

## Security properties we expect

- With an admin key configured, no admin, control, weight, or profiling operation works without it, on the server, every stage route, and the Python router.
- One client never reads or affects another client's requests, outputs, streams, sessions, cached state, uploaded voices, stored media, jobs, or results, including through chosen request IDs or hash collisions in cache keys.
- Request data never chooses a file path, URL, host, process argument, environment variable, shared memory name, IPC endpoint, import path, or object to deserialize beyond what the operator's media policy and config allow. Internal metadata keys are never settable by clients.
- Every request-driven resource is bounded: body and upload size, decoded media size and duration, frame and pixel budgets, steps and tokens, batch items, WebSocket messages, stream duration, sessions and connections, retained state, and memory per request. A small request must not crash, wedge, or exhaust a server, router, stage, or native server.
- Outbound fetches honor the media policy after redirects and DNS changes, with size caps and timeouts.
- Listeners resist cross-site requests and DNS rebinding where a browser can reach them.
- Stage IPC, shared memory, and host-shared files cannot be reached or pre-created by other local users to read data or run code.
- Secrets never appear in responses, errors, logs, profiler artifacts, config dumps, or requests to third parties.
- CI never gives code or text from an outside contributor a write token, secrets, persistent influence over self-hosted runners and caches, or control of a release.

## Components that matter most / least

- **Tier 1:** sections 1 to 5, 12 to 14, and 17, plus the request-reachable model code in section 9, the stage IPC trust boundary in section 6, and in section 16 the Voxt update channel, credentials and endpoint policy, remote clients, model downloads, entitlements, and local automation.
- **Tier 2:** the rest of sections 6 and 16, and sections 7, 8, 10, 11, 15, and 18.
- **Tier 3, still in scope:** model kernels and schedulers when request data can trigger memory corruption, crashes, or data crossing between requests (Triton kernels in `sglang_omni/utils`, FlashInfer JIT in `sglang_omni/sampling`, flash-attn in `sglang_omni/modules`), and section 19.

## How you rate severity

- **Critical:** code execution or arbitrary file write by A1 or A9, or by A6 against a default install. Bypass of a configured admin key that leads to the same. A forged Voxt update. An outside contributor obtaining a write token, secrets, or control of a release or a self-hosted runner.
- **High:** reading host files, loading a model or file the operator did not choose, or SSRF to internal or metadata addresses through request fields. Code execution or data access by A7 through stage IPC or host-shared files. A2 reading or changing another client's data. Use of admin operations despite a configured key. Memory corruption in native code reachable from request bytes. Theft of Voxt credentials. Persistent poisoning of CI runners or caches.
- **Medium:** one request, or a few, that crash, wedge, or exhaust a server, router, stage, or native server. SSRF limited to public hosts, or blind. Disclosure of paths, secrets, worker addresses, or internal hosts. Cross-site access to listeners with limited impact. What an unauthenticated client can do through admin routes when no key is configured, unless it reaches a Critical or High effect above, which then takes that rating.
- **Low:** issues that need an unusual operator configuration, hardening gaps without demonstrated impact, and denial of service that needs a large request volume, since rate limiting belongs to the operator.

## Anything to leave alone

- Code, weights, or pickles inside the model repository or directory the operator chose, including remote code its loader runs. Loading anything the operator did not choose is in scope.
- That a port is reachable because the operator bound it to a public address. Report what can be done through it.
- Model output quality, prompt injection that only changes generated text or audio, and resource use of legitimate large requests within configured limits.
- Bugs entirely inside SGLang, PyTorch, FFmpeg, MLX, CivetWeb, or other dependencies. Report them when SGLang-Omni uses the dependency unsafely, pins a version with a known advisory, or exposes the bug to untrusted input.
- Unit tests themselves, except where CI runs them on self-hosted runners (section 19).

## Documentation that may not match the code

- `docs/developer_reference/apiserver_design.md` says the multi-process launcher does not mount the profiling routes.
- The `openai_api.py` module docstring lists `/v1/fs/list` and `/v1/fs/file`, which the server does not register (the `qwen-omni` playground does).
- `launcher.py` mentions a `sglang-omni-server` command that is not installed.
- `docs/developer_reference/communication.md` describes Mooncake as configured cross-node movement and tunable acknowledgement and send queue settings that no shipped config path selects.

## Reports and patches

Give the entry point, the attacker label, a minimal request or input that shows the issue against this repository, and the file and function where the input reaches the sink. Patches should reject bad input with a clear client error, keep documented request shapes and defaults working, and add the smallest test that fails before the fix.
